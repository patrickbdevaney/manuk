## What the "727 vs 517 tokens per task" counts
It is `input_tokens + output_tokens` from the final `usage` of each run. `input_tokens` is only the UNCACHED input (about 6-10
per run); cache reads and cache creation are not in it. So the metric is >98% **model output**: thinking + tool-call
arguments + final text. No tool result and no tool definition is in it. (The `total` metric adds cache_read + cache_create.)

## Top 3 buckets of the manuk-vs-Playwright(+preload) gap
- **in+out (the 727 vs 517 metric): (1) out_thinking +118 (56% of the +210 gap), (2) out_toolargs +45, (3) out_text +45**
  (uncached input +3). Tool results are not in this metric at all, so the Wave-5 premise that bloated act/observe results
  explain the 727-vs-517 gap is NOT supported by it; the gap is Haiku producing more output (mostly thinking) per task.
  Turns are level (5.38 vs 5.35), so it is output per turn. Why manuk's results lead to more thinking is not shown here
  (hypothesis only: bigger, noisier observations; follow-up W5.T0.a).
- **total metric:** manuk is 42k LOWER overall, entirely because pw+preload's prefix is 47.7k larger. Where manuk is higher: (1) tool
  results re-read +4,082 (navigate observation is the bulk), (2) assistant output re-read +980, (3) out_thinking +118.
  So token work on the result/observation size (T1, T2) targets the `total` metric; T3 (smaller prefix) targets manuk's
  prefix, which is already below pw+preload's; the in+out Bar 2.2 branch is moved only by reducing thinking/output.

Method and caveats: per-call context from `usage` (stream blocks merged by message id; per-call sums reproduce the run
totals exactly); growth between calls is split into assistant tokens (run output apportioned by generated bytes) and the
remainder to tool results by result bytes, so per-tool numbers are an apportionment, not a tokenizer count. Thinking is
`output_tokens_details.thinking_tokens`; toolargs vs text split by bytes. B4 is Haiku, one chrome_ver, 3 runs.

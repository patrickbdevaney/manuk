# A float written into a line RE-FLOWS that line — in both directions

> Landed t1378. Gate: `a_float_reflows_the_line_it_joins` (`agent/tests/g_float_line_reflow.rs`),
> ten shapes, every number headless-Chrome-measured. Closes the one row `G_VI2_RESIDUALS` carried
> as *NAMED, MEASURED, NOT BUILT* since t1364.

## The defect, in one fixture

```html
<div style="width:400px">xxxx xxxx xxxx<div style="float:left;width:80px;height:20px"></div>yyyy</div>
```

```text
                                   chrome     before     after
  the float's own rect           [0 0 80x20]   same      same     (t1002 got this right)
  the text BEFORE the float        x = 80      x = 0     x = 80
  `yyyy`                        x=214.86 y=2   y = 26   x=214.86 y=2
  the BLOCK's height                 24          48        24
```

An `<img class="alignright">` inside a paragraph is exactly this shape, it is the most common float
on the content web, and doubling a paragraph's height is a large `dy` on the shape metric. Floats
appear on 60.4% of the declared corpus.

## The mechanism — a committed flush freezes the line

`layout_block` walks its children accumulating an `inline_run`, and flushes that run whenever
something that is not inline-level turns up. The float arm **flushed first and placed second**,
because CSS 2.1 §9.5 rule 6 — *"the outer top of a floating box may not be higher than the top of any
line-box containing a box generated by an element earlier in the source document"* — needs to know
where the last line's top is, and the only way to know that is to lay the run out.

Committing that flush costs the line in both directions at once:

- the text **before** the float keeps the x positions it was handed when nothing was in the way, so
  the float lands on top of it; and
- the text **after** the float has no open line to join, so it opens a new one.

The float's own rect was already Chrome-exact (t1002 fixed rule 6's placement half). Everything
around it was not.

## The fix — trial, discard, defer

The run is laid out as a **trial** into a scratch `Vec<LayoutBox>` that is thrown away. The trial
answers rule 6's question (*where is the last line's top, and how much room is left on it*), the
float is placed with that hint, and then:

- `inline_run` keeps its nodes,
- `cur_y` and `prev_margin` do **not** advance,
- the one real flush happens later, with this float already in the `FloatContext`.

So the whole run — the text before the float and the text after it — is line-broken **once**, around
the float. `layout_inline`'s `open_band` already consults the float edges; nothing in the line
breaker changed.

⚠ **The rewind is unconditional.** The tempting optimisation is to rewind only when the float
actually joins the line. `c2` refutes it: a 380px float in a 400px block cannot join, so Chrome drops
it to `y=24` — and *still* keeps `yyyy` on the first line, block height 24. **A float that cannot
join a line does not break it either.** Rewinding conditionally fixes `c1` and leaves `c2` at 48.

⚠ **It does not re-create the t1113-1120 side-table leak** (t1374 attached that constraint to this
design). An intrinsic probe poisons `pre_transform_rect` because it lays a subtree out at a **1e6**
available width and `or_insert` keeps the first writer. This trial runs at the same `cw`, the same
`pch` and through the same collect path as the committed pass, so every side-table write it makes is
byte-identical to the one that follows. The `intrinsic_probe` flag is deliberately **not** raised:
it changes `text_align` resolution, which would corrupt the very used-width the trial measures.

⚠ **Cost: one extra inline layout per float-that-follows-text**, and none at all when the pending run
is empty — a float that follows a block child, or that is a first child, takes the same path it
always did.

## The battery

Ten shapes, `--headless=new`, a 400px block, `monospace 16px/24px`, each case isolated behind a
`clear:both` so no earlier float overhangs the next wrapper. (That isolation is not cosmetic: a float
overflows a non-BFC parent, and the first measurement of this battery had case 3 reading `y=12`
because case 2's 380px float hung 12px into it.)

```text
                                            wrapper h    float rect      the text
 c1  text, then a float that FITS              24       [  0  0 80x20]  before → x=80
 c2  text, then a 380px float that does NOT    24       [  0 24 380x20] stays at x=0, yyyy joins
 c3  CONTROL — float FIRST, then text          24       [  0  0 80x20]  x=80
 c4  text wrapping to TWO lines, then float    48       [  0 24 80x20]  line 1 untouched
 c5  a <p> block, then a float, then text      48       [  0 24 80x20]  yyyy → x=80
 c6  text<br>second, then a float              48       [  0 24 80x20]  `second` → x=80
 c7  text, then a RIGHT float                  24       [320  0 80x20]  unmoved (it fits)
 c8  text, then TWO floats                     24       [0 0] + [80 0]  x=160
 c9  text, a 60px-tall float, wrapping text    48       [  0  0 80x60]  BOTH lines indented
c10  `xxxx ` float ` yyyy` (spaces both sides) 24       [  0  0 80x20]  ONE space survives
```

⭐ **`c10` is the row that says the run must be DEFERRED, not SPLIT.** Chrome puts `yyyy` at
`x = 128.16 = 80 + 38.53 + 9.63` — exactly one space between the two words, even though a float sits
between them in source order. The obvious alternative design, collecting the run in two pieces around
the float, drops that space: each piece is `first` again, so its leading white space is discarded.
Deferring one collection keeps it, for free.

⭐ **`c4` is the row that says only the LAST line re-flows.** Line 1 of a two-line run sits above the
float's band and Chrome does not re-break it. Because the band is queried by `y`, this falls out of
the design rather than needing a rule.

## How it was proven red

- **N1 — commit the flush** (restore the old arm, keeping the trial's boxes): `c1` reads 48. That is
  the defect exactly, and it is the mutation a future reader most plausibly makes.
- **N2 — pass `None` for the rule-6 line hint**: `c9` reads 24 instead of 48. The placement half
  (t1002) and the re-flow half are asserted by the same gate and neither alone passes it.
